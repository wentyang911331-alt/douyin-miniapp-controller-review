# 子代理协作文档

## 协作目标

通过 UI 子代理和前端子代理分别产出专业建议，由主控统一合并，保证页面调整既符合测评报告的视觉目标，也符合后续向抖音小程序迁移的代码准备口径。

当前阶段不需要后端子代理。

## 角色分工

### 主控

主控负责：

- 维护项目规范和需求边界
- 调度 UI 子代理与前端子代理
- 合并两个子代理的建议
- 识别冲突并给出取舍
- 在用户确认前阻止对原始 HTML 的修改
- 最终实施代码改动和验证

### UI 子代理

UI 子代理负责：

- 测评报告风格定义
- 标题、水印、说明入口、小浮窗的视觉方案
- 表格和排行榜的信息层级
- 移动端阅读体验
- 暗色和亮色模式下的视觉一致性
- 细节建议，包括间距、字号、边框、按钮状态、提示样式

UI 子代理不直接修改代码，先输出方案。

### 前端子代理

前端子代理负责：

- 现有 HTML 结构分析
- 小浮窗交互方案
- 水印实现方案
- 小程序准备约束下的代码整理建议
- 风险点识别
- 验证方式建议

前端子代理不直接修改代码，先输出方案。

### 后端子代理

当前不启用后端子代理。

只有出现以下需求时再启用：

- 数据改为接口拉取
- 需要后台配置或内容管理
- 需要用户登录、权限或账号状态
- 需要提交测试数据
- 需要服务端生成报告、图片或分享内容
- 需要埋点上报或远程统计

## 协作流程

1. 主控确保文档已落地并同步给子代理。
2. UI 子代理先启动，只负责圆角图标体系和可验收预览，不修改原始 HTML。
3. 用户验收 UI 图标方案。
4. UI 验收通过后，前端子代理再启动，负责实现方案、风险清单和必要代码建议。
5. 主控合并 UI 和前端方案，形成实施计划。
6. 用户确认实施计划。
7. 主控再修改原始 HTML。
8. 主控完成验证并更新必要文档。

## 当前开发节奏

当前从 1.0.0 基线推进到 1.1.0 页面实现，采用验收门控制：

1. UI 阶段：已完成。圆角图标体系包括主题切换、最佳徽章、排名角标、列显示、排序、模块信息、关闭弹窗等图标。
2. UI 验收：已通过。采用「圆角容器 + 圆角线性 SVG」；最佳徽章采用「星标 + 最佳」；排名角标保留 `#1/#2/#3`。
3. 前端阶段：已完成。实现标题、水印、说明小浮窗、功能移除和图标接入。
4. 验证阶段：已完成。主控完成本地页面验证，确认功能移除、说明浮窗和移动端阅读体验。
5. 版本阶段：已按项目规则更新版本记录，并需要随版本提交、打标签、推送 GitHub 备份。

## 子代理输出格式

每个子代理输出应包含：

- 结论摘要
- 建议清单
- 风险或待确认点
- 对另一个子代理的协作提醒

UI 子代理应额外包含：

- 视觉优先级
- 组件状态说明
- 移动端注意事项

前端子代理应额外包含：

- 代码改动范围
- 小程序迁移影响
- 验证清单

## 冲突处理

当 UI 建议和前端建议冲突时，按以下顺序决策：

1. 不破坏现有核心功能
2. 不影响移动端阅读
3. 不增加小程序迁移难度
4. 不引入不必要依赖
5. 保持测评报告风格

无法判断时，由主控整理为待确认问题交给用户确认。

## 修改保护

1.1.0 已完成 `controller-review(1).html` 的实现修改。后续新需求仍需先确认需求边界和版本号，再修改页面。

文档可以先落地和迭代；代码实现必须等待确认。
